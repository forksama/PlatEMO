# 城市巡逻 UAV 路径规划系统计划与方向

## 1. 项目目标

在 `C:/Repositories/PlatEMO` 下新建一个独立 Python 工程项目：

`C:/Repositories/PlatEMO/uav_path_planning_system`

该项目的主要目标不是重写现有 Matlab 算法，而是把现有 PlatEMO 中的 `DCMOCPSO` 算法与 `UAVPathPlanning` 问题模块工程化接入，形成一个面向“通信优化的城市巡逻 UAV 路径规划系统”。

系统最终希望做到：

- 让用户在 Web 页面上配置城市巡逻场景、通信参数、无人机参数和算法参数。
- 后端调用 Matlab 中已有的 `DCMOCPSO + UAVPathPlanning` 完成多目标优化。
- 前端展示候选路径、基站、建筑物、通信切换点、信号质量、覆盖率和 Pareto 解集。
- 将算法研究成果转化为一个可演示、可扩展、可继续工程化的系统原型。

## 2. 当前基础判断

本仓库已经具备较好的算法基础。

现有核心模块包括：

- `PlatEMO/Algorithms/Multi-objective optimization/DCMOCPSO/DCMOCPSO.m`
- `PlatEMO/Algorithms/Multi-objective optimization/DCMOCPSO/UAVPathPlanningSegment.m`
- `PlatEMO/Algorithms/Multi-objective optimization/MOCPSO`
- `PlatEMO/Problems/Multi-objective optimization/Real-world MOPs/UAVPathPlanning.m`
- `ARCHITECTURE.md`
- `DEVELOPMENT_WORK.md`
- `patent_notes/patent_disclosure_full_draft.md`

从现有材料看，算法设计已经相对清晰：

- `UAVPathPlanning` 负责构建无人机路径规划问题，包括城市环境、基站、建筑物、信号模型、切换算法、目标函数和约束。
- `DCMOCPSO` 负责对该问题进行分治式多目标优化。
- `UAVPathPlanningSegment` 负责把完整路径拆成多个子问题，使 DCMOCPSO 可以按路径段逐步求解。
- `MOCPSO_Ek_Flexible` 是 DCMOCPSO 内部调用的改进粒子群优化器。

本机环境也具备初步运行条件：

- Python 版本为 `3.10.4`。
- Node.js 版本为 `v24.15.0`。
- Matlab 可启动，版本为 `R2024b`。
- 当前 Python 环境尚未安装 `matlab.engine`，因此第一版不能只依赖 Python Matlab Engine，需要保留 `matlab -batch` 命令行调用方式。

## 3. 可行性结论

项目可行。

主要原因：

1. Matlab 算法侧已经有明确入口。

   PlatEMO 支持通过算法类和问题类组合运行。`DCMOCPSO` 已经能接受分段数、重叠航点数、`lambda`、`c_guide`、动态分组、动态变异、E_k 开关等参数。`UAVPathPlanning` 也已经能接受基站密度、速度、TTT、切换阈值、前瞻距离、安全裕度等参数。

2. Python 侧不需要重写算法。

   Python 工程只需要承担“系统层”的工作：任务管理、参数校验、调用 Matlab、保存结果、转换数据格式、提供 API、支撑前端展示。

3. Web 系统与算法模块边界清楚。

   Matlab 负责计算，Python 负责调度，前端负责交互与可视化。这种分工能避免把算法代码和工程代码混在一起。

4. 现有实验结果和专利草案已经能支撑系统功能设计。

   专利草案里的核心思想包括通信感知路径规划、上下文感知前瞻性切换、分治式多目标优化、阶段性 Pareto 筛选。这些都可以直接转化为系统功能模块。

## 4. 总体设计方向

推荐采用：

**FastAPI 后端 + Matlab 计算适配层 + React 前端 + 本地 SQLite/文件制品存储**

整体结构如下：

```mermaid
flowchart LR
    UI["前端 Web 界面"] --> API["Python FastAPI 后端"]
    API --> Task["规划任务管理"]
    Task --> Store["SQLite 元数据 + 本地文件结果"]
    Task --> Adapter["Matlab 调用适配层"]
    Adapter --> Matlab["PlatEMO / DCMOCPSO / UAVPathPlanning"]
    Matlab --> Result["结果文件 result.mat / result.json / 日志"]
    Result --> Store
    Store --> API
    API --> UI
```

由于 DCMOCPSO 可能运行较久，不能让 HTTP 请求同步等待 Matlab 完成。

任务管理模块需要负责：

- 创建任务 ID

### Matlab 适配模块

这是后端最关键的模块。

需要提供统一接口：

- 输入：规划参数、任务 ID、结果目录
- 输出：结果文件路径、日志文件路径、状态

底层建议保留两种实现：

1. Matlab CLI Runner

   使用 `matlab -batch` 启动 Matlab 脚本。优点是稳妥、隔离性好、不依赖 Python `matlab.engine`。缺点是每次启动 Matlab 成本较高。

2. Matlab Engine Runner

   使用 Python 里的 `matlab.engine` 常驻调用 Matlab。优点是后续任务启动快，更适合交互式系统。缺点是需要安装 Engine 包，且要处理常驻进程稳定性。

第一版建议优先做 CLI Runner，Engine Runner 作为可替换接口保留。

### 结果转换模块

Matlab 结果不适合直接给前端使用，需要转换成稳定 JSON。

建议转换内容：

## 6. Matlab 接入方向

### 6.1 不建议直接改动现有算法文件

第一阶段不建议修改：

- `DCMOCPSO.m`
- `UAVPathPlanning.m`
- `UAVPathPlanningSegment.m`
- `MOCPSO_Ek_Flexible.m`

原因：

- 这些文件已有实验和论文/专利意义。
- 当前任务是做系统工程接入，不是继续改算法。
- 直接修改算法文件会增加验证成本和回归风险。

### 6.2 建议新增 Matlab 桥接脚本

可以在 Python 工程中新增一个 Matlab 桥接脚本，例如：

```text
uav_path_planning_system/backend/app/matlab/scripts/run_planning_job.m
```

该脚本的职责是：

- 接收 Python 写好的任务参数文件
- 添加 PlatEMO 路径
- 创建 `UAVPathPlanning` 问题对象
- 创建 `DCMOCPSO` 算法对象
- 执行求解
- 提取最终种群
- 提取目标函数值
- 提取切换细节
- 提取场景数据
- 保存 `.mat` 和 `.json` 结果

这样既能复用现有算法，又不会污染原始算法目录。

### 6.3 Matlab 调用方式选择

第一阶段推荐：

- 默认使用 `matlab -batch`
- 同时预留 `matlab.engine` 接口

原因：

- 当前 Python 里还没有 `matlab.engine`。
- CLI 方式更容易先跑通。
- 后续安装 Engine 后，可以切换到常驻 Matlab worker，提高交互速度。

## 7. 前后端交互流程

典型用户流程如下：

1. 用户进入系统首页。
2. 前端加载默认场景和默认参数。
3. 用户调整 UAV 参数、通信参数、切换算法参数和 DCMOCPSO 参数。
4. 用户点击“启动规划”。
5. 后端创建任务，返回任务 ID。
6. 前端进入任务监控状态。
7. 后端后台调用 Matlab。
8. Matlab 执行 DCMOCPSO 优化。
9. Matlab 输出结果文件。
10. 后端解析结果并更新任务状态。
11. 前端获取结果并展示路径、指标和切换细节。
12. 用户选择某条 Pareto 候选路径查看详情。
13. 用户导出结果或继续创建对比任务。

## 10. 技术路线对比

## 10.1 方案 A：Matlab CLI + FastAPI + React

这是推荐第一版方案。

优点：

- 最容易跑通。
- 不依赖 `matlab.engine`。
- 每个任务独立启动 Matlab，隔离性较好。
- 出错后容易通过日志定位。

缺点：

- Matlab 启动成本高。
- 不适合高频交互。
- 多任务并发需要额外控制。

适用阶段：

- 原型验证
- 课程/论文/专利成果演示
- 单机系统

## 10.2 方案 B：Matlab Engine 常驻 Worker

这是推荐第二阶段方案。

优点：

- 任务启动更快。
- 更适合交互式参数调试。
- 可以维护 Matlab 会话状态。

缺点：

- 需要安装 Python Matlab Engine。
- 常驻会话需要管理异常恢复。
- 长时间运行可能存在稳定性问题。

适用阶段：

- 原型已经跑通后
- 需要更好交互体验时

## 10.3 方案 C：MATLAB Compiler SDK 或 Production Server

这是推荐后期生产化方案。

优点：

- 部署更正式。
- Python 与 Matlab 耦合更低。
- 适合服务化。

缺点：

- 授权和部署复杂。
- 打包成本高。
- 对当前阶段偏重。

适用阶段：

- 系统要部署给多用户使用
- 需要正式服务化运行

## 13. 风险与应对

## 13.1 Matlab 调用风险

风险：

- Python 当前没有 `matlab.engine`。
- Matlab 启动较慢。
- Matlab 出错后错误信息可能较长。

应对：

- 第一版使用 `matlab -batch`。
- 所有 stdout/stderr 都落盘。
- 后端只负责识别成功/失败。
- 后续再接 Engine Runner。

## 13.2 长任务风险

风险：

- DCMOCPSO 实验可能运行较久。
- HTTP 请求不能一直等待。

应对：

- 任务异步执行。
- 前端轮询任务状态。
- 日志和结果按任务 ID 保存。
- 后续引入队列和 worker。

## 13.3 结果格式风险

风险：

- Matlab 内部数据结构不一定适合直接给前端。
- 后续算法字段可能调整。

应对：

- 后端定义稳定 JSON 格式。
- Matlab 原始结果 `.mat` 保留。
- 前端只依赖后端标准结果。

## 13.4 可视化复杂度风险

风险：

- 三维城市可视化较复杂。
- 建筑物、路径、基站、切换点全部展示容易拥挤。

应对：

- 第一版先做二维俯视图。
- 使用图层开关。
- 后续再升级三维视图。

## 13.5 现有代码污染风险

风险：

- 如果直接改 Matlab 核心算法，可能影响已有实验结果。

应对：

- 第一版只新增 Python 工程和 Matlab 桥接脚本。
- 不修改 `PlatEMO/Algorithms` 和 `PlatEMO/Problems` 下的核心文件。
